# Contributing

Thanks for taking a look. This repo is a detection-engineering portfolio, but it follows the same review rules as a small production detection team.

## Ground rules

* **Sigma is the source of truth.** Edit files in `rules/sigma/`, never the generated output in `rules/compiled/`.
* **Every rule needs tuning notes.** `falsepositives`, `references`, `description`, and ATT&CK tags are enforced by `python -m pipeline.lint`.
* **No real customer data.** Telemetry in this repo is synthetic. Do not add production logs, hostnames, usernames, or IPs that are not documentation ranges (RFC 5737 / RFC 1918).
* **Keep generated artifacts in sync.** CI fails if `rules/compiled/` or `docs/attck-coverage.md` drift.

## Adding a detection

1. Copy an existing rule in `rules/sigma/` and give it a new UUID (`uuidgen` or Python's `uuid.uuid4()`).
2. Fill in `title`, `description`, `references`, `author`, `falsepositives`, `level`, `tags`, and a valid `logsource`.
3. Run the pipeline:

   ```powershell
   .\.venv\Scripts\python.exe -m pipeline.lint
   .\.venv\Scripts\python.exe -m pipeline.compile
   .\.venv\Scripts\python.exe -m pipeline.coverage
   .\.venv\Scripts\python.exe -m pipeline.heatmap
   .\.venv\Scripts\python.exe -m pytest
   ```

4. If the rule needs lab evidence, add a scenario to `pipeline/labgen.py` and a test that asserts the rule fires.
5. Commit the rule **and** the regenerated artifacts together.

## Adding a correlation

Correlations are YAML specs in `correlations/` consumed by `pipeline/correlate.py`. Keep the base Sigma rules single-event; put "N events in T seconds" logic here. Add a unit test in `tests/` with a positive and a negative case.

## Changing the dashboard

`docs/index.html` is generated by `pipeline/report.py`. Do not edit it by hand. After changing the template:

```powershell
.\.venv\Scripts\python.exe -m pipeline.report
```

If you change the ATT&CK matrix, regenerate `docs/assets/attck-heatmap.svg` with `python -m pipeline.heatmap` and re-take the hero screenshot described in `docs/runbook.md`.

## Pull requests

* Keep changes focused; one rule or one pipeline change per PR is ideal.
* Describe the detection gap or bug being fixed.
* Include the command output that proves the change works.
